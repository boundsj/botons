# Botons: notes for agents

Botons is a self-hosted server for always-on AI agents ("botons"), each with its own chat, routines, memory and workspace, running on the local `claude` or `codex` CLI. Node 24+ runs the TypeScript directly (type stripping) with `node:sqlite`; the web app is React + Vite. See README.md and docs/ (docs/README.md is the index) for installing, running and operating it; docs/development.md for working on it.

## Commands

```sh
npm ci
npm run typecheck                      # server and web
npm test                               # the fast tests (seconds): node:test, in-process, no browser, Botons server or outside network
npm run test:full                      # every test, with the mock provider and fake CLIs (needs Chromium and bubblewrap); deploy runs it
node --test server/test/<name>.test.ts # one file
npm run build                          # the web app
npm run check:public                   # before every commit; before a PR add: -- --commits origin/main..HEAD
npm run perf:chat -- --out /tmp/perf    # the chat in headless Chrome with a 1000-message fixture: renders, input latency, memory, history paging (own temp server)
npm run check:preview                  # the file viewer in headless Chrome: HTML previews sandboxed (opaque origin, no /api), SVG, the no-preview card (own temp server)
npm run check:firstrun                 # a fresh install's first run in headless Chrome: claim, setup, the first Boton and its reply, all saying Botons (own temp server; or --url and --approve against a running one, as docker-smoke.sh does)
npm run check:browser                  # the managed browser in real Chromium, as a turn starts it, on a temp profile and a loopback page (browser.test.ts needs Chromium too)
npm run check:avatars                  # the Boton avatars in headless Chrome from a version-24 database: migration, states, motion pause, the builder by keyboard (own temp server)
npm run check:sidebar                  # the sidebar in headless Chrome by keyboard and emulated touch: groups made, renamed, deleted; row menus (pin, move, move to group); drag to arrange by mouse and by touch long-press (swipes still scroll); collapse with counts; search; live sync; the chat left alone (own temp server)
npm run check:reactions                # chat reactions in headless Chrome: the picker by keyboard (quick row, More's search and any emoji), chips that take one off, refusals as toasts, a second tab live both ways, the Boton's with the real `botons` CLI, follow-ups (run, withdrawn, off in Settings), approvals untouched, reload and an older page, render counts (typing and opening 0 rows, a reaction 1), an emulated phone's long press, swipe and tap; the picker and catalog load only when wanted (own temp server)
npm run check:timestamps               # chat times in headless Chrome in another zone over several days: day dividers (Today, Yesterday, the date), burst times after a 30-minute pause, a run chip's own time, the exact time on hover (desktop) and a tap (emulated phone) and to a screen reader, Load earlier, 0 rows rendered while typing (own temp server)
npm run check:operations               # Settings as the owner in headless Chrome: health, a failing then fixed push (fake ntfy), runs to check, server events, a restart, the summary's privacy, backup rehearsals (own temp server)
npm run check:recovery                 # a backup restored onto a fresh machine with the real backup, restore and doctor (from a copy without node_modules): the restored server cold-starts with every Boton, look, group, pin, skill, grant, message, session and index; the schema before upgrades; rehearsals; a data folder it can't write; SIMULATED no space (own temp servers)
npm run check:connectors               # Settings → Connect a service in headless Chrome: guided add, a test against a fake loopback MCP server (key never shown), exactly which Botons have it, a stale save refused, history (own temp server)
npm run check:api-keys                 # Settings → API keys in headless Chrome: environment key, save (masked, field cleared, nothing in page storage), test against a fake loopback model list, remove with its fallback named (own temp server)
npm run check:starters                 # New Boton → a starter template in headless Chrome: what it needs, guidance to Connect a service, the exact grants, install paused, setup check, a passing and a failing test run on the mock brain, an edit taking a pass away, turn on, an override from the Routines panel, a stale review refused (own temp server)
npm run check:config                   # Settings → Move to another server in headless Chrome: export from a populated server (no secret in the file, page or log), preview and import on a fresh one (Full access only once ticked, spending caps shown, left out and kept again by a tick, never what was spent), secrets put back, the same configuration exported again (two temp servers)
npm run check:api-brains               # a Boton on an API key in headless Chrome against a fake loopback Anthropic API: new Boton, chat that makes a routine (Workspace sandbox, needs bubblewrap), cost on the reply, spending caps, the key's evidence (own temp server)
npm run dev                            # web 127.0.0.1:5173, API :7778, data ./.botons-dev, mock provider
npm run doctor -- --skip-clis          # read-only check of an install; here only with a temp BOTONS_HOME and a free BOTONS_PORT
npm run migrate:names                  # moves an install off earlier names (backup first); acts on a real install, so here only with HOME set to a temp folder
docker compose config --quiet          # the Compose files; scripts/docker-smoke.sh builds and runs the image (needs Docker)
```

`npm start`, `serve`, `pair`, `backup`, `restore`, `doctor`, `deploy`, `service:install` and `backup:install` act on a real install (`~/.botons`, port 7777, `~/.config/botons/env`, systemd), and `docker compose` on the real `botons` project and its volumes. Don't run them unless asked; run `pair`, `backup`, `restore` or `doctor` only with `BOTONS_HOME` set to a temp folder, and Docker only through `scripts/docker-smoke.sh` (its own `botons-smoke` project). `npm run dev` takes `BOTONS_HOME` and `BOTONS_PORT` from the shell when they are set.

Installing, upgrading or diagnosing an install for its owner follows `.claude/skills/install-botons/SKILL.md`: it lists what needs the owner's go-ahead first (exposing the server, firewall, proxy or DNS changes, credentials and sign-ins, privileged host changes, anything that risks data or touches a running server).

## Layout

- `server/src`: `index.ts` starts the server (exit 78 on a bad setting or database); `app.ts` wires everything and listens; `api.ts` holds the HTTP routes; `auth.ts` covers pairing (and the owner's claim) and device and Boton tokens; `setup.ts` the first-run setup and the access mode checked on every request; `audit.ts` the audit log of consequential actions; `trash.ts` the server's trash (deleting files, Restore, the daily inbox cleanup and its pins, sizes) and `disk-usage.ts` counts what folders take; `cards.ts` the transcript cards Botons post and the owner answers in the chat (the protocol and its checks are `shared/cards.ts`; what an answer does is decided there, never by the client); `capabilities.ts` the owner's view of what a Boton may do; `engine.ts` runs chat turns and routine runs (queues, retries, pause, drain, restart recovery); `store.ts` holds most SQL (`auth.ts`, `approvals.ts`, `connectors.ts` and `skills.ts` query their own tables); `skill-packages.ts` reads skill packages from `BOTONS_HOME/skill-packages` as text only (never run), and `skills.ts` installs one exactly as the owner reviewed it; `templates.ts` the saved templates and installing one, and `starters.ts` the built-in starters with what each needs, the owner's review of exactly what installing one grants (a key that refuses a stale review) and its setup check (it runs nothing); `starter-gate.ts` decides when a starter's routine may be turned on (a test run of its current settings, or the owner's override) and `Store.updateRoutine` refuses every other way; `schema.ts` is the database schema; `prompt.ts` builds the text sent to the agent CLIs; `providers/` runs the claude and codex CLIs (plus `mock`) and the API key brains (`api-brain.ts` the tool loop, `api-wire.ts` the Anthropic and OpenAI wire protocols, `api-tools.ts` the tools, `api-history.ts` their sessions); `sandbox.ts` is the bubblewrap sandbox their Workspace tools run in; `rates.ts` the per-model prices and `spend.ts` the spending caps; `isolation.ts` lists what Workspace Botons can't read; `browser.ts`, `browser-proxy.ts` and `browser-policy.ts` are the managed browser (the built-in `botons_browser` connector; `browser-handover.ts` is the owner's handover, which the web app shows as a live view over the chat with `shared/live-view.ts`; `browser-handoff.ts` and `shared/handoff.ts` are a Boton's `browser_handoff` card: requested, taken over, handed back); `oauth.ts`, `oauth-connections.ts`, `mcp-client.ts`, `outbound.ts` and `work-feed.ts` are OAuth connectors (sign-in, tokens, the guarded outbound requests, the work feed); `webhooks.ts` and `hooks.ts` verify and serve webhooks; `portable.ts` exports and imports the owner's configuration without secrets (its own format version, apart from the schema); `config.ts` reads the env vars; `cli/botons.ts` is the `botons` CLI that Botons run.
- `shared/types.ts` is the API contract between server and web; `shared/util.ts` holds helpers both use; `shared/wake.ts` controls quiet transcript visibility and wake labels; `shared/effort.ts` holds the effort levels each provider takes (checked where they are set); `shared/look.ts` is a Boton's look, a button-bot Boton (its parts as fixed names, random looks, and the mapping of earlier looks, which `shared/look-tater.ts` and `shared/look-critter.ts` read, to their closest Boton) and `shared/boton.ts` draws it as layered SVG with detail by size; `web/src/components/BotonBuilder.tsx` is the one builder wherever a Boton is made or edited; `shared/brand.ts` holds the brand marks (the Boton mark, the wordmark, the app icon and the favicon), and `node scripts/icons.ts` rewrites `web/public/favicon.svg` and `icon.svg` from them (`--png` also draws the home-screen PNGs in headless Chromium). The palette lives in `web/src/styles.css` and follows `docs/brand`.
- `web/src`: the React app (`state.ts` and `api.ts` hold its state and API client).
- `scripts/`: deploy, backup, restore, pair, doctor, the systemd installers, dev, check-public and `docker-smoke.sh`.
- `Dockerfile`, `compose.yaml`, `docker/` (the image's `botons` command, the Tailscale and Caddy overlays), `.env.example`, `botons.env.example`; `docs/DOCKER.md` is the operator guide for them, `docs/RELEASING.md` the release and publishing checklist.
- `server/test`: `helpers.ts` (`startServer`, `freePort`, `noRealClis`, `useTestCodexHome`, `until`, `tempDir`) and `fixtures/` (recorded CLI output and fake CLIs).

## Rules that protect running installs

- The system prompt (`systemPrompt()` in `prompt.ts`) keys each provider session: `sessionKey()` hashes it with the provider id, and `engine.ts` starts a new session when the key changes. Any change to its text, or to what it interpolates, starts a new session for every Boton. Change it only on purpose and say so in the PR. Other prompt text (context block, chat input, routine prompts) doesn't reset sessions.
- Earlier names live in one place: `shared/legacy-names.mjs` (every earlier name, for one release) and what uses only it to move an install: `server/src/legacy-upgrade.ts` (the server's first start moves the data folder and database; `npm run deploy`, the installer and `npm run migrate:names` move the service, env file and release folder), `docker/legacy-names.sh` (Compose). Deprecated settings and commands still work, hidden: they never appear in docs, help text or the app, and doctor names each once. Don't add an earlier name anywhere else; the old-names guard fails on one.
- `schema.ts` holds the schema at `SCHEMA_VERSION`: `openSchema` creates it in an empty database, opens a database at that version, and refuses any other (the server exits 78). A schema change bumps `SCHEMA_VERSION` and teaches `openSchema` to upgrade the previous version in place, with a test that upgrades a database holding data and ends with the schema a new database gets.
- `scripts/backup.ts`, `scripts/restore.ts`, `scripts/doctor.ts`, `scripts/migrate-names.ts` and the `botons` CLI run without `node_modules`, so everything they load imports Node builtins only (`import type` is fine): `server/src/{backup,config,disk-usage,env-init,isolation,legacy-upgrade,lock,log,rehearsal,schema,tailnet,util}.ts` (`rehearsal.ts` is the restore rehearsal's child process), `server/src/providers/{cli-check,process}.ts`, `server/src/cli/*.ts`, `scripts/install-service.ts`, `scripts/install-backup-timer.ts`, `shared/legacy-names.mjs`, `shared/look.ts`, `shared/look-tater.ts`, `shared/look-critter.ts` and `shared/seeded.ts` (the schema upgrade migrates looks with them), `shared/effort.ts` (doctor checks levels with it), `shared/files.ts` (doctor's storage thresholds) and `shared/util.ts`. A test enforces this.
- The Docker defaults are safety settings: the port is published on `127.0.0.1`, data and logins live in volumes, `.env` (which may hold `TS_AUTHKEY`) never reaches the server's environment, and the overlays drop the app's own port. `server/test/docker.test.ts` checks them; change them only with the owner.
- Auth, isolation (and the API brains' sandbox, `sandbox.ts`), SSRF, webhook signatures, file serving (with the HTML preview sandbox, `PREVIEW_CSP` in `files.ts`), the managed browser (its proxy, routing and read-only actions) and approvals are security code: never loosen them, and test every change.
- Tests never touch a real install: `startServer` gives a temp `BOTONS_HOME`, 127.0.0.1, a `freePort()` in 17000–19999, `BOTONS_NO_TAILSCALE=1`, the mock provider and `noRealClis`; call `useTestCodexHome` before anything that runs codex. Never point anything at `~/.botons`, `~/.claude`, `~/.codex` or port 7777, and never call the real claude or codex CLI from a test. API key brains in tests talk only to `fixtures/fake-model-api.ts` on loopback (createApp's `apiKeys.testEndpoints`, set in code, never from a setting) with fake keys; never a real provider.
- To check a change against real data, copy the database with `VACUUM INTO` into a private temp folder, run on the copy, and delete it afterwards. Never commit data from a real install.

## Keep it publishable

Anything that reaches GitHub may be published one day: files, commit messages, commit author and committer, branch and tag names, PR titles, descriptions and review comments, and issue text. So:

- No personal or environment details: real names, emails, usernames, machine or host names, tailnet names, IP addresses, home folders, employers, links to private docs, trackers or chats, account or org ids, the owner's MCP servers, plugins, connectors or skills, real chat or routine content, screenshots or dumps of a real install.
- Use placeholders: owner "Sam" (`sam@example.com`), host `myhost`, tailnet `example-tailnet.ts.net`, home `/home/you`, other domains under `example.com`. Test Botons take placeholder names (Kevin, Stuart, Bob, Dave).
- No history of this project in code, comments or docs: no "v1", "legacy", "previously", "used to", "migrated from", commit hashes, or issue and milestone numbers. Say why the code is the way it is, not how it got there. Commit messages describe the change itself under the same rules; merge with rebase or fast-forward, or write the merge commit's title yourself (no "#N", no user or branch names).
- Recorded CLI fixtures: before committing, replace home paths, account details, org ids, emails and the recorder's own MCP servers, plugins, connectors and skills with placeholders. Keep the structure and every value the tests parse.
- Allowed on purpose (don't "scrub" these): version numbers such as `SCHEMA_VERSION`; env var names, `~/.botons`, port 7777 and other runtime names; the credential folders listed in `isolation.ts` (common tools, not anyone's setup); products Botons supports (Tailscale, ntfy, GitHub, Linear, Slack, Sentry, claude.ai connectors); text about the present ("no longer exists"); third-party ids in recorded output (API paths, capability names).
- Notes about one machine (where it runs, how it is deployed there, host names) stay outside the repo: in agent memory, or in a `*.local.md` file (gitignored).
- Botons is MIT-licensed (`LICENSE`, and `license` in each package.json); `SECURITY.md` and `CONTRIBUTING.md` are its policies. Publishing the repository, changing its visibility, changing the license or its holder, and adding a CODE_OF_CONDUCT or author fields are the owner's call. `docs/RELEASING.md` lists what to check before publishing. Runtime dependencies must be permissively licensed (`server/test/licenses.test.ts`).
- `npm run check:public` catches the shapes of emails, tailnet names and addresses, home folders, share links, account ids, secrets and binary files, and the product's earlier names outside the legacy-names module and the few files it allows (`oldNames`). Real names, host names, employers, IP addresses and MCP setups are caught only by the private terms list (`$PRIVATE_TERMS_FILE`, default `~/.config/private-terms/botons.txt`, outside the repo, one case-insensitive regex per line) or by you; add a new private detail to that list when you meet it. The Public workflow runs the check on every pull request, including the PR's commits, title and description. When it flags real data, replace the data; don't widen its allowlists.

## CI runtime policy

Pull requests run two required checks: `Node 24` (cached `npm ci`, typecheck,
`npm test`; it passes without work on docs- and image-only changes) and
`check:public`. A pull request may merge when both are green; the full suite runs
at deploy (`npm run deploy` runs `npm run test:full` before the web build). The
full tier (Node 24 and 26, browsers, recovery, Docker, Debian installer, the Codex
helper, the Node 26 handover quarantine) runs weekly, by hand, and on pull
requests labelled `full-ci`; label risky security, installer, browser or Docker
work and wait for those jobs. `npm test` keeps to the fast list in
`scripts/test-tier.mjs`; new files default to the full tier. Do not delete tests
merely for taking time; move them to the full tier or replace real waits with
injected clocks while preserving assertions. Use `docs/TEST-RUNTIME.md` and timing
artifacts for measurements. Never promise a runtime reduction without measuring it.
