# Security

## Reporting a vulnerability

Please report it privately, never in a public issue or pull request: use [**Report a vulnerability**](https://github.com/boundsj/botons/security/advisories/new) on the repository's **Security** tab (GitHub's private vulnerability reporting). Include what you found, how to reproduce it, and what it lets an attacker do. You should hear back within a week; a fix and an advisory follow once it is confirmed.

Only the latest release and `main` get security fixes.

## What Botons trusts

Botons is a single-owner server: it runs agent CLIs, as the server's user, on the owner's behalf. Read these before exposing it.

- **A paired device is the owner.** It can read every chat, change every Boton and approve what Botons ask for. Devices pair once: a new device asks and shows a code, and the owner approves that code from a paired device or on the server's machine (`npm run pair -- --approve`); the owner's own Tailscale devices pair with one click. The server can't tell a browser from a Boton that leaves out its token, so a code is never a credential: only the device that asked holds the secret the approval unlocks, and a code seen in a chat pairs nothing. Tokens and request secrets are stored hashed. A new server is claimed the same way, with the first approval only from the server's machine, so reaching the page first is not enough to own it. No Boton token can ask, approve or pair.
- **The access mode** (`local`, `tailscale`, `lan`, `public`) refuses requests from other networks on the app's port before anything else runs. It only narrows what the listeners expose; widening exposure is always a change the owner makes on the host. Public needs HTTPS and auth, and no device can choose a mode that would refuse itself.
- **The audit log** records pairing, access, setup, approvals and what each Boton was given, by whom; never a secret. Botons can't read it, and nothing in the API deletes it.
- **A Boton with Host access is the server's user.** It can read and change everything that user can: the database, every workspace, the CLI logins, the server's environment. In Docker that is everything in the container.
- **A Boton with Workspace access** runs in the CLI's sandbox, which keeps it out of other workspaces, `BOTONS_HOME`, the CLI logins and the common credential folders listed in `server/src/isolation.ts` (plus `BOTONS_PRIVATE_PATHS`).
- **Runs started by a webhook** use Workspace access by default, even for a Boton with Host access, and then can't change the instruction files later turns load. The owner can turn that off for a routine (**Webhook runs use Workspace access** in its settings; `webhookWorkspace: false`): then a Host-access Boton's webhook runs have Host access, like its other turns, and the instruction files get no such protection. Only the owner can turn it off, never a Boton, and it never gives a Workspace Boton more than Workspace access.
- **Webhooks** need the routine's own key and, where configured, a signature; they are rate limited. A signed sender's signature is checked on the exact bytes before the body is parsed, and a form body has at most 1000 fields. `BOTONS_HOOKS_PORT` serves webhooks alone, for the internet, while the app stays private. A webhook run never carries on the chat's session, whatever the routine's `session` says: it sees none of the chat unless the owner shares the latest messages with that routine's webhook runs (`webhookHistory`, at most 20, inside a budget of its own), and then each run starts a fresh session with those alone, so no run sees more. Only the owner can share them; a Boton can only set it back to 0. Whoever holds the routine's key can read each run's reply.
- **Ask first** pauses a covered tool call for the owner. **Allow once** allows that one call with exactly the arguments shown (only a Bash command's description, the model's own words about it, may differ), and only once: another call, even an identical one made at the same moment, waits for a decision of its own.
- **Botons asking Botons**: a Boton answers each colleague's asks in a turn of their own, apart from the owner's messages and other colleagues' asks: none still waiting is in that turn's input, or in the chat replayed to a new session, and the owner's reactions go only to the owner's turns. The turn still has the Boton's conversation so far, as any turn does.
- **Local MCP servers** (a connector that is a command on this computer) start in the Workspace sandbox's view of the computer for every Boton, whatever its access: bubblewrap with an empty read-only root, the system's programs and libraries, the folders on `PATH` and the folders the command and its absolute-path arguments name, each read-only, and an empty `/tmp` of their own; no workspace, shared folder, data folder or other home folder, by any path, a second mount (bind mount) of one included. A connector naming something in those is refused. Unlike Workspace commands they keep the host's network (Unix sockets stay refused), so the Botons given one and its saved environment limit what it is handed, not what it can reach over the network. Without bubblewrap none start (`server/src/connector-launch.ts`).
- **Outbound requests** (routine callbacks, OAuth connectors) refuse private and local addresses unless allowed by `BOTONS_CALLBACK_ALLOW` or `BOTONS_OAUTH_ALLOW`, and follow no redirects.
- **The browser**: every request's `Host` must be one of the server's names (against DNS rebinding), and changes need a same-origin JSON request.

## Deploying it safely

- Keep the app off the open internet: the default listens on `127.0.0.1` and the machine's Tailscale address, and the Docker setup publishes on `127.0.0.1`. Use Tailscale (or HTTPS behind a reverse proxy) to reach it from other devices; never plain HTTP across a network you don't control.
- Keep authentication enabled during first-run setup and pairing. Approve the code on the server instead of disabling auth.
- Pairing admission is capped at 50 unexpired requests; new requests receive 429 when full. Accepted codes remain valid until expiry, but sustained unauthenticated traffic can delay new requests. Keep the app private and use proxy rate limits when exposing it.
- Never put credentials in the server's environment: Botons with Host access can read it.
- Back up `BOTONS_HOME` (`npm run backup`, or `botons backup` in Docker): it holds chat history and webhook keys, and the backups are private to the server's user.
- `npm run doctor` (`botons doctor` in Docker) flags auth off, exposed interfaces, plain HTTP, missing backups and a broken sandbox.
