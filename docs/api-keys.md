# API keys and Botons on an API key

Besides your own Claude Code or Codex, a Boton can run on your own Anthropic or OpenAI API key, with Botons running the agent loop itself. You pay the provider per use.

## API keys

**Settings → API keys** keeps your own Anthropic and OpenAI API keys. With a key, a Boton can run on it: pick **Claude (Anthropic API key)** or **OpenAI (API key)** as its brain (see [Botons on an API key](#botons-on-an-api-key) below).

- **Where a key lives.** A saved key is kept in the database, as OAuth connector tokens and the ntfy token are, so it is in every backup and comes back with a restore. It is never shown again: the API, events, logs and the audit log say only whether there is one and where it comes from. Workspace Botons can't read the database; Full computer Botons run as the server's user, so they could. Without a saved key, Botons uses `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` from the server's environment, read at start; a saved key always takes its place. Agent CLIs get neither, from either source (they get only an allowlist of variables).
- **Changing one.** Paste a key and Save; the field clears once it is saved, and the page never stores it. Each save or removal names the version of the key the page last saw, so a page that is out of date can't overwrite a newer key (409). Remove the saved key takes off only the saved one, and says first what is used from then on: the environment's key if one is set, else none. A key that comes from the environment is removed there, followed by a restart. Removing a key here doesn't revoke it with the provider, and older backups still hold it.
- **Test key** asks the provider for the list of models the key can use (`GET https://api.anthropic.com/v1/models` or `GET https://api.openai.com/v1/models`, to those fixed addresses only, never following a redirect). It sends no prompt and generates no text, so it uses no tokens. One test at a time per provider, at most 6 a minute, each in the audit log. The result is a fixed word (works, refused, forbidden, rate limited, provider unavailable, unreachable or an unreadable answer) and, when it works, the models: their ids, plain display names and lifecycle, kept only in their expected shape (an id that could hold the key is left out). Nothing else the provider says is kept, error text included. A test is kept with the key it was of: if the key changes while it runs, the test stops and its result is never shown as the new key's.
- **Capabilities** come only from evidence. The provider's model list: Anthropic's says whether a model takes images and which effort levels it has; OpenAI's says neither. And the key's own turns: once a turn on the key finishes with a reply, a tool call or an image, that model shows chat, tool use or images as seen working (with when), until the key is replaced or removed. Anything not seen yet (realtime voice, speech-to-text and text-to-speech always, since Botons don't use them) is unknown, never guessed from a model's name, and Botons never sends a paid request just to find out.

`GET /api/api-keys`, `PUT` and `DELETE /api/api-keys/:provider` (`anthropic` or `openai`, with `generation`) and `POST /api/api-keys/:provider/test` are for paired devices only; Boton tokens get 403.

## Botons on an API key

A Boton whose brain is **Claude (Anthropic API key)** or **OpenAI (API key)** runs on the key from Settings → API keys, with no CLI: Botons runs the agent loop itself. Each turn sends the conversation to the provider's fixed address (Anthropic's Messages API or OpenAI's Responses API, streamed), runs the tool calls the answer asks for, sends their results back, and stops when the model answers without one. Everything else works as with a CLI brain: chat, routines on a schedule or a webhook, memory, skills, `botons` commands, approvals and connectors, except **Ask first**: Botons' tool loop has no step that pauses for you, so Ask first rules don't apply to these Botons (their capabilities say so).

- **Its tools** are a shell, reading, writing and editing files, and the tools of its Botons connectors (OAuth and library ones; never a CLI's own setup). A connector's tool list (names, descriptions, input schemas) and each result (its text and its structured content, all of it) have the connector's own secrets (its saved headers and environment values, the OAuth token the turn sends) and every API key taken out before the model or anything kept sees them; a tool whose name holds one is left out. A result's images, files and links are named, never fetched or passed on. Tool definitions are bounded too (16 KB a schema, 200 KB in all). A command that is only a `botons …` command (no pipes, redirects, `;`, `&&`, `$` or backticks) runs as the CLIs run it, reaching the Botons server with the turn's token; its webhook-run and approval limits are the server's, as for every Boton.
- **Workspace access** runs every command, file read and file write in an OS sandbox ([bubblewrap](https://github.com/containers/bubblewrap) 0.11 or newer, Linux), and what it may affect is its workspace and the shared folder (none in webhook runs), nothing outside them. Its root is empty and read-only; of the host it sees only the system's own trees (`/usr`, `/etc`, `/opt` and the like), the folders on its PATH and Node's install, each through a read-only overlay (a folder another filesystem is mounted inside, such as `/snap`, is left out, since the kernel can't overlay it): no home folder, no data folder with its database and keys, no other workspace, no `/var`, and an empty `/tmp` and `/run`. The paths Workspace Botons can't read (`server/src/isolation.ts`, plus `BOTONS_PRIVATE_PATHS`) are hidden too where they fall in that view. Through an overlay a named pipe (FIFO) or socket file of another program is the overlay's own, so writing, reading or connecting to it never reaches that program, and device files don't open; and a seccomp filter refuses to make a Unix socket at all, so no socket of a desktop, ssh-agent, D-Bus, Docker or a database is reachable, by any path, link or the abstract namespace (io_uring and the kernel keyrings neither). It has its own network with only its own loopback: the host's loopback, private networks and the internet aren't there. It sees no other process, gets no file descriptor of the server's, and only a short list of environment variables (never the server's, never a key). Its `.claude` folders are read-only, and in webhook runs the instruction files too. Programs that need a Unix socket of their own (a local database server, a browser) don't run there. The workspace is your folder too: a program of yours that watches it (a file, or a named pipe you put there) sees what the Boton writes, as it is meant to. Before a Workspace Boton's first command, Botons checks the sandbox on the machine (the filter on, and a named pipe of its own outside getting nothing through the view); without bubblewrap, or where the namespaces, the overlays or the filter can't be had (not Linux, a processor other than x64 or arm64, a container that forbids them), a Workspace Boton on a key doesn't run, and its turns say why before anything is sent. Nothing falls back to a weaker sandbox. **Full computer access** runs the same tools as the server's user, outside any sandbox.
- **Bounds.** At most 40 requests to the model a turn, 16 tool calls an answer (4 at a time), 2 minutes a command (the model may ask for up to 10), 32 KB of output a command, and the Boton's time limit for the whole turn. Stop ends the request and every command it started. Botons never sends a request twice and never runs a turn again after one of its tools did something: a provider error after that fails the turn (it says so), so nothing runs twice; before that, an overloaded or unreachable provider counts as a network error, and a routine run is retried as usual.
- **Its session** is kept by the server, in `BOTONS_HOME/api-sessions` (Workspace Botons can't read it), as the provider's own items, the model's reasoning included, passed back unchanged. A request's body is at most 600 KB exactly as sent (its instructions, tool definitions and conversation, and the images the message attaches, as base64, so an image of about 400 KB is the most one message can carry): the oldest exchanges are left out first (and the reasoning bound to the full conversation with them), then the oldest tool output of the current one, each replaced by a note so every call keeps its result. When even that isn't enough (a new input too big on its own, or a turn whose own answers outgrow it), nothing is sent and the turn says what to do. That is a bound on what Botons sends, not a model's context window, which may be smaller.
- **Usage and cost.** Each reply carries its tokens and an estimated cost, as does each routine run (Usage tab too). The estimate is the tokens the provider reported times the rates in `server/src/rates.ts`, copied from the providers' price pages (the date they were checked is there); it is not the bill. A model with no rate there, or a promotional rate past its end, has no known price: its cost is shown as unknown, never guessed.
- **Spending caps** are in the Boton's settings, under Spending: a daily cap (from midnight in the Boton's time zone) and a cap a run for each routine, in US dollars of that estimate. Botons keeps one row per request (`api_requests`), counted on the day it was sent: a turn that runs past midnight counts its later requests on the new day. Before each request, in one step, the caps are read as they are then (a cap added, lowered or removed during a turn applies from its next request; one already sent stays counted) and the most it could cost (every input token at the dearest input rate, its whole answer at the output rate) is written as its row, so a crash or another turn counts it too; the request goes only if that fits in what is left, with its answer's length lowered to fit, and the turn stops (with what it did so far) when not even a short answer fits. A request whose answer broke off or was stopped, or whose usage report is missing or doesn't add up, stays counted at that most, since the provider may have billed it; one still reserved when the server starts again is held the same way. With a cap set, a model with no known price doesn't run, and neither does a capped Boton on a day (or a run) that already has a request with no known price. Only you can set caps (`GET` and `PUT /api/bots/:id/spending`, paired devices only, audited); a Boton can't see or raise its own. Caps bound Botons' estimate, not the provider's bill.
- **The key** goes only into the request's header, to the provider's fixed HTTPS address, never following a redirect. A turn uses the key in use when it starts and only that one: if it is removed or replaced while the turn runs (or the saved one goes and the environment's takes its place), the turn stops before its next request and says so; the next turn uses the new key. Every key Botons holds is taken out of everything that comes back (the model's text, drafts, a tool's output, a connector's result, the provider's errors) before it is shown, kept or sent on, and no request body is sent while it holds one. In what the session keeps, the model's text and tool arguments are redacted; signed or encrypted reasoning that holds a key can't be changed, so it is left out; a tool call whose arguments held a key is never run; and an answer with a key where nothing can be changed (an id) is refused whole. That redaction covers the keys and their common encodings, not every way a model could transform one. A key is never in a tool's environment, argv, the log or an event. `npm run check:api-brains` drives the whole of it in headless Chrome against a fake Anthropic API on loopback.
