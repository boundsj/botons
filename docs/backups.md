# Backups, restore and moving to another server

Commands here are the installer's `botons backup` and `botons restore`. From a checkout or release folder use `npm run backup` and `npm run restore --`; in Docker see [DOCKER.md](DOCKER.md).

## Backups

`botons backup` (and the daily backup timer, at 03:30) writes `backups/<UTC time>/` in `BOTONS_HOME`: `botons.db` (a `VACUUM INTO` snapshot that passed `integrity_check`, safe while the server runs), `workspaces.tar.gz` (`workspaces/`, `shared/`, `templates/` and each Boton's browser profile in `browser/`, without its caches) and `manifest.json`. The folder is private (0700). It keeps the newest 14 backups and never deletes a file it did not make. If tar fails, the database copy is kept, no older backup is deleted and the run exits 1. `BOTONS_BACKUP_RSYNC_TO=host:path` also copies each new backup there.

The server also makes one, the same way, when it starts on a database it must upgrade to a newer schema, before changing anything; if that backup fails, it leaves the database as it was and exits 78.

## Restore

To restore, stop the server and run `botons restore` (it finds the service's `BOTONS_HOME` as `botons pair` does):

```sh
botons stop
botons restore --list                         # the backups, oldest first
botons restore latest                         # what it would do; changes nothing
botons restore latest --yes                   # or a name from --list, or a backup folder's path
botons start
```

For a systemd service run from a checkout, the same steps are `systemctl --user stop botons`, `npm run restore -- --list` (and so on), then `systemctl --user start botons`.

It refuses while a server uses the data folder, and deletes nothing: the current database (with its `-wal` and `-shm` files), `workspaces`, `shared`, `templates` and `browser` move to `before-restore-<time>/` in `BOTONS_HOME` first, and a restore that fails part-way (a full disk, say) puts them back and says what to do. A backup from an older schema version is upgraded at the next start; one from a newer version is refused. The same steps restore into another `BOTONS_HOME`, or onto a new machine where it does not exist yet (it is created, private): workspace paths are stored relative to it, and devices paired before the backup stay paired; the claude and codex sign-ins are not in a backup, so sign in again there. A data folder the user running it cannot write is refused before anything changes, and the server refuses to start on one (exit 78): run both as the folder's owner.

## Health and backups in Settings

**Settings → Health and backups** shows whether the database, the scheduler and at least one brain work and whether the server is accepting work, each failure as a fixed reason with a next step (a database that is locked, damaged, read-only or on a full disk; a brain not found or not signed in) rather than its error text; how push notifications to the current ntfy server, topic and token have gone since the server started or they last changed (not set up, turned off, or the last push and, when it failed, why in a fixed word such as refused or unreachable with where to look, how many failed in a row and the last that went through, with a button to send a test: one at a time, at most 10 a minute, each in the audit log); free disk space where the data lives and the database's size (flagged below 1 GiB or 5% of the disk); and the backups: the newest one's age (flagged when it is over 2 days old, or when there is none), how many are kept, what each holds (database and workspaces, or database only when archiving failed), backups that stopped part-way, and the commands above to back up and restore. Backing up and restoring stay commands on the server: a restore needs the server stopped. A status summary to paste when asking for help lists the same checks, the app and brain versions, build and schema (each only in its expected shape, else `unknown`) without Boton names, paths, addresses or error text. `GET /api/operations` returns the same to paired devices, with no paths, ntfy server, topic, CLI output or error text; `GET /api/health` keeps its details, error text included, for paired devices. The push and disk checks are not part of `GET /api/health`, so a failing ntfy server or low disk space alone never fails a deploy's health check.

### Rehearse a restore

**Rehearse a restore** (in **Settings → Health and backups**) checks that a backup would restore with the running release, without stopping the server or touching the data folder: the server copies the backup's database into a private folder (`run/rehearsal/` in `BOTONS_HOME`, emptied at every start), runs SQLite's integrity check, upgrades the copy to the server's schema as a restore and the next start would, checks it again, reads the workspaces archive through (gzip's checksum included) and checks every member as the restore does (regular files and folders only, only under `workspaces/`, `shared/` and `templates/`, no `..` or absolute paths), then deletes the copy. It unpacks nothing and runs no other program; it never follows a link in a backup folder, and it stops at 8 GiB of database, 64 GiB of archive or 256 GiB unpacked, without room for the copy, or after 30 minutes. It runs in its own low-priority process with a small heap and none of the server's environment, one at a time and at most 6 an hour (`POST /api/backups/rehearse` with a backup's name or `latest`, paired devices only), each in the audit log. The result keeps only times, the backup's name, fixed words (passed, or why not: a damaged database or archive, a schema this release does not restore, an upgrade that failed, links or stray paths in the archive, a limit reached, a restart while it ran), schema numbers, file counts and the version that ran it. A rehearsal cut off by a shutdown or crash reads as interrupted. The section also shows the release, build and schema the server runs, and for each backup whether this release's restore takes it (its own schema, or the one before, upgraded at the next start), going by the backup's manifest. A rehearsal is not a restore: restoring stays the command above.

## Moving your configuration to another server

There are two ways to carry a Botons server elsewhere, for different jobs:

- **A full backup** (`botons backup`, put back with `botons restore`, both above) is the whole server: the database with every chat, memory, token, sign-in, connector secret, API key and webhook key, and the workspaces. It is the way to recover from a lost or broken machine. Those secrets are in it as they are in the database, unencrypted: keep backups on the server's own disk (the folder is private) or on storage you trust with the secrets themselves, and encrypt one before it leaves (for example `tar -C ~/.botons/backups -cz <name> | gpg --symmetric -o botons-backup.tgz.gpg`, then the reverse on the new machine before `botons restore <folder> --yes`).
- **A configuration file** (**Settings → Move to another server → Export configuration**, `GET /api/config/export`) is your deliberate setup without any secret: Botons (name, title, instructions, look, brain, model, effort, access, timezone, paused, connectors, skills, Ask first and Always allow rules, browser sites, the spending cap a day on API-key turns) with their routines (each with its spending cap a run), the skills library with each skill's earlier texts, state and package source, the connectors (library entries with their command, arguments and URL, OAuth connectors by URL, each one's request policy and whether it was on), your name, timezone, primary Boton, push server and topic and the reactions that start a follow-up, your saved templates (never the built-in ones), and the sidebar's groups and pins. It never holds chats, memories, workspace files, connector env or header values, URL queries, OAuth sign-ins or tokens, webhook keys, signing secrets or callback URLs, the ntfy token, API keys, devices or Boton tokens, browser profiles, sessions, approvals, the audit log, or what API-key turns have spent (that account stays on the server and in its full backups). A connector's command line is read by its structure, and each credential in it becomes `<left out by the export>`, short ones too: the value of a flag named as one (`--token=…`, `--password -x`, the argument after `--api-key`), a `NAME=value` whose name is one (`API_KEY=…`), a header's value (`Authorization: Bearer …`), a URL's user name, password, query and #fragment (the query's names are kept in the list of what was left out), and anything key-shaped. Each argument stays one argument, and a credential's whole value goes, however many words it has; an argument holding quoted or structured text (an `sh -c` line, JSON) goes whole if any credential is in it, or if it can't be read exactly without running it. It leaves out more than it must rather than less, and names each place so you can put it back. Text you wrote, such as instructions and skills, is exported as written: the export names any that holds something shaped like a credential so you can check it before you share the file, but it can't promise to catch every secret in prose. That check covers every text in the file: instructions, routines, templates, package fields and each skill's earlier texts, named by which one and when it was replaced, never by what was found.

**Import a configuration…** in the same section reads a file and shows what it would do before anything changes: each Boton with its brain (one this server lacks is swapped for one it has, with the model and effort left out), model, effort, computer access, rules, connectors (and which of them are already set up and on here, so usable at once), skills, browser sites and routines; each skill and connector; the settings that would change; the sidebar; what in the file looks like a credential; and what you will need to do by hand. You choose there which Botons to make (one whose name is in use is left out unless you choose it), their brains, whether to keep this server's skill or connector of the same name or use the file's, whether to take the file's settings, and how to treat the sidebar. Nothing is widened by the file alone: Full computer access (and webhook runs with it) and Always allow rules come only when you tick them for that Boton. Importing makes exactly what the preview showed, in one transaction (all or nothing), and is refused if the file, your choices or this server changed since you looked. Every routine arrives off, webhooks get new URLs and keys, connectors arrive turned off without their secrets (at a new request policy, so no earlier approval applies) and OAuth ones signed out, and no token, session or sign-in is carried over. The managed browser stays the server's own: a file can't add a library connector under its name. The import is in the audit log, with each Boton made and what it was given. Then follow its list: enter connector secrets and sign in OAuth connectors in **Settings → Connectors** and turn them on, give webhook senders their new URLs, sign each brain in, enter the ntfy token, and turn on the routines you want.

The file is JSON with `format` `botons-config` and its own `version` (5), apart from the database's schema, and up to 16 MB. A server reads every version up to its own, upgrading older ones as it reads them (a version-1 file has no templates and doesn't say which reactions start a follow-up, so the importing server keeps its own; a version-2 file has no spending caps, so its Botons arrive with none, as the preview says), and refuses a file from a newer Botons, a field it doesn't know (in a look too), a missing one, bytes that aren't UTF-8, a broken character (a lone surrogate) in any text or key, a key such as `__proto__`, and a package source path that isn't one folder name. Your saved push access token is kept only when the file names the same push server (scheme, host and port); for another server it is removed, never sent there, and the same holds when you change the server in Settings. Saved templates arrive under new ids and never widen anything: Full computer access, Full access webhook runs, and connectors, skills or a brain this server won't have are left out of them, as the preview says, routine by routine. They are shown exactly when the import that made them is committed, even if the server stops part-way: it finishes putting them in place when it starts again. Spending caps arrive only on the Botons and routines an import makes, which are new here with an account of their own from $0 (what they spent where the file was made never comes with it); the preview shows each cap, whether it counts on the brain the Boton arrives with, and a model with no known price, and arriving without the file's caps is your tick alone. An import never raises, clears or restarts the caps or spending of a Boton already here, and records each Boton's caps in the audit log. Reading a file runs, fetches and opens nothing. `POST /api/config/import/preview` (`file`, `choices`) and `POST /api/config/import` (`file`, `choices`, the preview's `fingerprint`) are for paired devices only.
